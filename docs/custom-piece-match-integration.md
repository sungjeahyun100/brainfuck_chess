# 커스텀 기물 덱 및 게임 통합 계약

상태: 5단계 구현

## 덱 참조와 버전 정책

저장 덱은 커스텀 기물을 표시 이름이나 런타임 타입 문자열만으로 참조하지
않는다. 각 기물은 `id`, 불변 `version`, 서버 계산 `contentHash`,
`exposedPieceKey`를 함께 저장한다. 기존 로컬 덱에는 `customPieces: []`를
보충하는 하위호환 읽기 경로가 있다.

덱은 선택 당시 버전에 고정된다. 편집 화면은 활성 최신 버전과 덱에 고정된
과거 버전을 함께 조회하며, 새 버전이 있으면 사용자가 명시적으로
“최신 버전으로 업데이트”해야 배치와 포켓 참조가 바뀐다. 삭제되었거나
조회할 수 없는 버전은 경고와 함께 게임 사용 불가로 처리한다.

## 권위 있는 게임 생성

단일/봇 게임의 `/api/games`와 멀티플레이어 방 시작은 모두
`resolve_custom_packages`를 사용한다. 이 경계는 인증 소유자, 활성 상태,
불변 버전, 콘텐츠 해시와 대표 키를 저장소에서 다시 확인한다. 요청에는
점수, 원문 스크립트 또는 컴파일 정의를 받지 않는다.

승인된 패키지는 기본 정의와 합쳐져 게임의 `GameState.piece_definitions`와
`custom_piece_manifest`에 설치된다. 서버 덱 점수 계산, 시작 기물 생성,
포켓 생성, legal move, 행동 적용, 공격 범위와 AI는 이 게임별 정의 집합을
공유한다. 내부 의존 기물은 런타임 정의에는 포함되지만 덱 카탈로그에는
대표 기물만 노출된다.

현재 존재하지 않는 친선전·경쟁전 모드나 제한 정책은 추가하지 않았다.
향후 사용 정책이 생기면 분산된 게임 핸들러가 아니라 위 패키지 해석 경계에
검사를 추가할 수 있다.

## 표시, 재접속과 복원

서버 저장 레코드의 표시 이름과 승인된 이미지가 게임 정의 snapshot에
포함된다. 업로드 이미지는 검증된 바이트를 data URL로 고정하므로 이미지
저장소의 최신 상태를 다시 조회하지 않고 양쪽 클라이언트가 같은 자산을
표시한다. 내부 상태 전환 뒤에도 해당 게임 정의의 visual 정보가 사용된다.

진행 중 게임 조회와 방 재접속은 `GameStore`의 동일 `GameState`를 반환한다.
엔진 JSON snapshot은 정의 전체, manifest, 현재 내부 타입과 포켓 상태를
포함하며 `restore_game_snapshot`이 정의 hash를 검증하고 프로그램 캐시만
재생성한다. 따라서 원본 기물 수정 또는 비활성화는 이미 시작된 게임에
영향을 주지 않는다.

현재 저장소와 게임 저장소는 모두 인메모리 시제품이므로 서버 프로세스
재시작을 넘는 영속 복구는 지원하지 않는다. DB adapter 도입 시에도
`GameState` snapshot을 그대로 저장하고 최신 커스텀 기물 레코드로
재구성해서는 안 된다.
